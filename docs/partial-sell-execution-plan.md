# 부분매도 기능 — 실행계획서

> **문서 목적**: 전량 매도만 가능한 현재 시스템을 **종목·수량 기준 부분 매도**로 확장하기 위한 실행 순서, 산출물, 완료 기준을 한곳에 정리한다.  
> **상세 체크리스트**: `docs/TASKMASTER-partial-sell.md`

---

## 1. 배경·목표

| 항목 | 내용 |
|------|------|
| **목표** | 사용자가 보유 종목을 고르고 **매도할 주식 수(`sell_count`)**만 입력해 일부만 매도할 수 있게 한다. |
| **불변** | **매수 로직·DB 스키마(마이그레이션 없이 컬럼 활용)** — `inventories`는 기존처럼 lot(구매 건별) 레코드로 유지. |
| **매도 규칙** | 동일 종목을 여러 lot으로 보유한 경우 **FIFO(선입선출)** — `created_at`이 빠른 lot부터 차감. |

---

## 2. 현행 vs 목표

| 구분 | 현행 | 목표 |
|------|------|------|
| API 입력 | `inven_id` (단일 lot) | `stock_id`, `sell_count` |
| 매도 범위 | 해당 lot **전량** 소프트 삭제 | `sell_count`만큼만 lot에서 차감·필요 시 lot 삭제 |
| UI | lot 단위 드롭다운, 수량 입력 없음 | 종목(`stock_id`) 단위 선택 + 수량 입력 |
| 시세 반영 | 현재가 × 해당 lot 전체 수량 | 현재가 × `sell_count` |

## 4. 실행 단계 (권장 순서)

### Phase A — 백엔드 (필수)

1. **요청 검증**  
   - `stock_id`, `sell_count` (정수 ≥ 1, 해당 유저의 해당 종목 **합산 보유수량** 이하).
2. **FIFO 처리**  
   - `user_id` + `stock_id`로 `inventories` 조회 → `created_at ASC` 정렬.  
   - 남은 `sell_count`를 0이 될 때까지 앞 lot부터 처리:  
     - lot `amount` > 남은 매도분 → `amount` 감소(UPDATE).  
     - lot `amount` ≤ 남은 매도분 → 해당 lot 소프트 삭제, 남은 매도분에서 차감.
3. **거래·발행 반영**  
   - 최신 시세 × `sell_count` → `stock_trades` 1건 (`calc_amount`, `title`에 수량 명시).  
   - `stocks.stock_count`를 `sell_count`만큼 증가(유통 복원).
4. **트랜잭션**  
   - 위 단계를 **단일 DB 트랜잭션**으로 묶는다.

**산출물**: `createSell`이 `inven_id` 의존을 제거하고, 전량 매도는 `sell_count = 합산 보유수`로 동일 동작.

### Phase B — 프론트엔드 (필수)

1. 드롭다운을 **`stock_id` 기준**(합산 보유 수량 표시)으로 변경.  
2. `sell_count` 입력 필드 추가, 선택 종목의 `max`와 동기화, 기본값은 전량(기존 UX에 가깝게).  
3. 실시간 표시: 현재가 × `sell_count`, 손익 등.  
4. 제출 시 `stock_id`, `sell_count` 전송.  
5. 성공 후 인벤토리 캐시 무효화·UI 갱신 (`inventory.blade.php`와 연동).

**산출물**: `sellForm.blade.php` 및 필요 시 `inventory.blade.php` 수정.

### Phase C — 검증 (필수)

- 부분 매도 후 잔여 수량·재매도.  
- 전량 매도(한 종목 전체).  
- 다 lot·FIFO 시나리오(문서 `TASKMASTER` Task 5).  
- 초과 수량·0·음수·미로그인 등 예외.

**산출물**: QA 시나리오 통과 또는 Feature 테스트.

### Phase D — UX 보강 (선택)

- 가중 평균 매수단가 표시, 25/50/75/100% 퀵 버튼 등 — `TASKMASTER` Task 4.

## 5. 리스크·주의

| 항목 | 내용 |
|------|------|
| 트랜잭션 | lot 여러 건 수정 시 부분 커밋 금지. |
| 동시성 | 동일 유저·동일 종목 동시 매도 시 정합성 — 1차는 트랜잭션 내 재검증, 필요 시 잠금·큐는 후속. |
| 하위 호환 | 기존 `inven_id` 전송 클라이언트는 **동시 지원하지 않으면** 한 번에 전환하고 릴리스 노트에 명시. |

### 5.1 현재 `createSell`·연동 시 추가 점검

- **`stock_trades` 첫 거래**  
  이전 거래가 없으면 `before_amount`/`now_amount` 소스가 null이 될 수 있다. 부분 매도 리팩터 시 **동일 패턴**을 쓰면 예외가 남을 수 있으므로, 첫 매도·첫 매수 경로를 함께 점검한다.

- **잔고 갱신과 동시성**  
  “마지막 `stock_trades` 한 행을 읽어 이어 붙이는” 방식이면, 동시 매도 두 건이 같은 `before_amount`를 읽을 수 있다. 트랜잭션만으로는 부족할 수 있어 **`lockForUpdate`** 등으로 잔고·관련 행을 직렬화하거나, 잔고를 **단일 행 갱신**으로 모델링하는지 검토한다.

- **수량·금액 정밀도**  
  `inventories.amount`는 **정수(주 단위)** 스키마다. 금액은 부동소수점 누적 오차를 피하도록 **원 단위 정수·`decimal` 일관**을 유지한다.

- **FIFO와 손익·표시**  
  체결은 `stock_trades` 1건으로 묶어도, 사용자에게 보이는 **실현 손익·매수단가**는 FIFO로 깎인 lot과 어떻게 대응시킬지(가중 평균 vs FIFO 실현) **표시 정책**과 맞춰야 한다(Phase D·§7 참고).

- **이중 제출·재시도**  
  버튼 연타·네트워크 재시도로 동일 매도가 두 번 들어가지 않게 할지(멱등 키·짧은 윈도 중복 방지 등) 정한다(§7).

- **권한 스코프**  
  `stock_id`만 받을 때 **`user_id` + `stock_id`**로 조회한 inventory만 변경하는지 재확인한다.

- **감사·디버깅**  
  거래 1건이어도, 운영상 lot별 차감 내역을 **로그/별도 기록**에 남길지는 선택 사항이다.

## 6. 완료 기준 (Definition of Done)

- [ ] `stock_id` + `sell_count`로 부분·전량 매도가 모두 동작한다.  
- [ ] FIFO가 코드·테스트 또는 재현 절차로 확인 가능하다.  
- [ ] 현금 잔고, `stock_trades`, `stocks.stock_count`, 인벤토리 수량이 시나리오별로 일치한다.

## 7. 구현 전 결정 사항 (담당자 판단)

아래는 코드만으로 자동 결정되지 않거나, 제품·운영 정책을 정해야 하는 항목이다.

| 구분 | 결정할 내용 | 비고 |
|------|-------------|------|
| API 전환 | `inven_id` **완전 제거** vs **한동안 병행** | 병행 시 분기·테스트 부담 증가. 외부 클라이언트 없으면 제거가 단순. |
| 동시성 1차 범위 | 트랜잭션 + 재검증만으로 출시 vs **첫 버전부터 행 잠금** | 트래픽·동시 매도 빈도에 따라. §5.1 참고. |
| 손익·단가 UI | 매도 직전 **예상 손익**을 어떤 단가 기준으로 보여줄지(가중 평균·FIFO 실현 등) | Phase B 실시간 표시·Phase D와 연결. |
| 중복 요청 | **서버 멱등/중복 방지**를 넣을지, 프론트 비활성화만 할지 | 금융성 데이터면 서버 쪽 권장. |
| lot별 감사 | lot 차감 내역을 **DB/로그에 남길지** | 장애 분석용이면 유리. 스키마 추가 없이 로그만도 가능. |
| 공지 | API·UI 변경을 **릴리스 노트·사용자 공지**로 할지 | 내부용이면 최소화 가능. |

**이미 스키마로 고정된 것(별도 결정 불필요)**  
- 주 수량은 **정수**(`inventories.amount` bigInteger). 소수 주 매도는 현 스키마로는 불가.
